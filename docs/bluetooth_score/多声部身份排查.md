# 多声部杂音与身份排查

2026-10-25，排查基于蓝牙分支2d86834。用户反馈：82秒小星星的第一遍正常，约26秒进入多声部后出现杂音，屏幕声部计数始终为1；手机端设备能力暂时看不到。

当前结论是**实板与RTL仿真存在差异，根因尚未确认**。不能据仿真排除实板身份坍缩，也不能把杂音直接认定为时序或削顶。本轮保持原播放器、分配器、混音和身份策略，加入被动观察点用于定位。

## 已检查的链路

上传记录本身只有时间/音高/力度/门长，不带MIDI通道身份。播放器给同时活动的音符分配0～15逻辑身份；音高相同也须独立分配。23位事件经过CDC、蓝牙适配和顶层选择，再由32物理声部分配器接收。

专项测试使用当前小星星在0、26、52、78秒的真实起音组合，只缩短仿真的时间和门长，经实际协议上传与CRC、RAM、播放器、CDC、顶层选择、音源及显示状态链路。四组分别得到身份位图0001、000F、00FF、FFFF；8声部组中多个MIDI60仍为不同身份。逐声部相位、频率、力度及混音与独立参考值比较通过。LCD计数与原子状态传递也能显示1/4/8/16；此结果不代替实板状态。

## 本地诊断版

本次修改只在 `E:\gowin\fpga-instrument-bt-score`。新模块 `src/bt_identity_monitor.sv` 已加入原 `keyboard_adsr.gprj`，只记录真实valid/ready握手，不修改事件、播放或音源分配，不增加反向等待。原设置/演奏页不变；扩展既有more INFO内容：

- SRC：参考时钟域播放器已发送的活动逻辑身份，16位。
- RX：音频域音源已接收的活动逻辑身份，16位。
- H：分配器实际按住的32个物理声部位图。

SRC先用原服务快照CDC送到音频域；三项再通过more原子快照送到像素域并在帧边界显示。低82位原曲库状态保持，扩展高64位只作诊断；两端快照延迟不同，起止瞬间可能短暂不同，应观察稳定和弦。

按既定分工，由用户关闭旧编辑页、重新打开本目录原工程，重新综合/P&R、检查时序并下载。进入设置→more→FLASH INFO（矩阵more页R3C3）后，应看到 **ID CHECK 02 / SRC RX HOLD**。这行标记确认观察的是新诊断位流；GitHub此前归档的11:27位流不包含本次诊断，不要将其当作新版。

## 十秒受控测试

先在FPGA打开上述INFO页，再在App导入 [identity_four_notes.mid](../../android/examples/identity_four_notes.mid)，选择全部轨道/全部通道/移调0。预览应为4条、10秒、最大4同时音、MIDI60～72。下载后主动播放。

该文件四音同时起音，分别在4、6、8、10秒松开。每次播放会先清空旧自动声部，因此正常情况下：

| 播放时间 | SRC | RX | H | 按住声部数 |
| --- | --- | --- | --- | --- |
| 0～4秒 | 000F | 000F | 0000000F | 4 |
| 4～6秒 | 000E | 000E | 0000000E | 3 |
| 6～8秒 | 000C | 000C | 0000000C | 2 |
| 8～10秒 | 0008 | 0008 | 00000008 | 1 |
| 结束后 | 0000 | 0000 | 00000000 | 0 |

H为按住状态，ACTIVE还可能包含正常释放尾音。上述稳定区间应排除刚起音/刚松音的快照延迟。如果App提示设备只允许1声部，这本身就是板上返回旧能力的证据，应记录提示，不绕过限制。

对首个稳定四音和弦记录完整的SRC/RX/H：

| 观察 | 排查方向 |
| --- | --- |
| SRC本身只有一个置位 | 播放器分配、下载数据或实际固件版本 |
| SRC有四位，RX只有一位 | CDC、适配、顶层选择或这些路径的硬件时序 |
| SRC/RX均有四位，H只有一位 | 音源分配器接收/所有权提交或相关硬件时序 |
| 三项均正确，普通VOICES仍为1 | 普通计数/显示路径，不能据此断定只用一个声部 |
| 三项均正确，声音仍异常 | 继续检查每声部采样、增益、串行音频和实际时序 |

这份文件的生成命令为 `python scripts/generate_bluetooth_examples.py --identity`，记录CRC32为6643E19E。App实际解析与转换记录比对见 `reports/bt_identity/four_note_parser.log`。
