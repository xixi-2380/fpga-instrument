# 手机向 FPGA 下载曲谱：通信协议 v1.0

日期：2026-10-23。本文是待实现的接口约定，不代表软硬件已经完成或通过实物验证。除另行注明外，字段均为无符号整数，多字节字段使用小端序。

## 1. 目标与实现边界

- 安卓手机通过经典蓝牙 SPP 连接现有 BC417 模块，模块通过 TTL UART 与 FPGA 交换数据。
- 手机导入 MIDI、解析声部与速度变化、转换成本文音符记录。FPGA 不解析 MIDI、PDF、图片或 MP3。
- 手机下载完整首曲子，FPGA 校验成功后播放；不按蓝牙到包时间实时演奏。
- v1 使用单个曲谱 RAM 存储区：新上传一旦获准开始，旧曲立即失效；失败后需要重新上传。断电丢失曲谱。
- v1 不支持断线续传、多个曲目、曲名传输、实时调速、协议层鉴权或主动状态推送。歌曲名称由手机管理。
- 播放、暂停、继续和停止属于 v1。第一阶段可以先发布仅支持单声部的 FPGA 实现，手机以能力信息为准。

## 2. 物理连接与 UART

| 项目 | 约定 |
|---|---|
| 模块底板供电 | 用户已确认 VCC 为 5V；不等于 UART 引脚可承受 5V |
| UART 电平 | 模块 TX/RX 为 3.3V；FPGA 所用 IO Bank 必须兼容，否则加电平转换 |
| 接线 | 模块 TXD → FPGA RX；模块 RXD ← FPGA TX；共地 |
| 串口格式 | 8 数据位、无校验、1 停止位，即 8N1；无 RTS/CTS 流控 |
| 初期目标波特率 | 9600 bit/s；先确认模块现值，再将模块与 FPGA 配为一致 |
| 后续目标波特率 | 115200 bit/s；双方一致配置并实测后启用 |

手机的 SPP 连接没有 UART 波特率设置。本协议不包含 AT 配置指令；模块配置与业务通信分开调试。不得仅根据 BC417 芯片丝印认定固件型号、默认波特率或 KEY/EN 引脚功能。

## 3. 帧格式

一帧按下列顺序连续发送。UART/SPP 是字节流，一次接收回调可能只有半帧，也可能包含多帧。

| 字节偏移 | 字段 | 长度 | 说明 |
|---:|---|---:|---|
| 0 | SOF | 2 | 固定字节 `A5 5A` |
| 2 | VERSION | 1 | 固定 `01` |
| 3 | CMD | 1 | 请求为 `00`～`7F`；响应为请求 CMD 按位或 `80` |
| 4 | SEQ | 2 | 请求序号；响应原样返回 |
| 6 | LEN | 2 | PAYLOAD 字节数，范围 0～256 |
| 8 | PAYLOAD | LEN | 命令参数或响应数据 |
| 8+LEN | CRC16 | 2 | 低字节在前 |

总帧长为 `10 + LEN`，最多 266 字节。长度字段表示载荷长度，不含帧头或 CRC。

### 3.1 CRC16

- 算法：CRC-16/CCITT-FALSE，又称 CRC-16/IBM-3740。
- 宽度 16，poly=`0x1021`，init=`0xFFFF`，RefIn=false，RefOut=false，XorOut=`0x0000`。
- 覆盖 VERSION、CMD、SEQ、LEN、PAYLOAD；不含 SOF 和 CRC16 自身。
- 标准校验：ASCII `123456789` 得到 `0x29B1`；传输字节为 `B1 29`。

### 3.2 接收与失步恢复

1. 搜索 `A5 5A`，读取固定头，检查 LEN，再接收指定长度的载荷和 CRC。
2. 已进入一帧后，载荷内出现 `A5 5A` 是普通数据，不能提前重启解析。
3. LEN 大于 256、CRC 错误、接收 FIFO 溢出、帧内连续 200ms 没有新字节，或从 SOF 开始超过 1000ms 仍未收齐：丢弃当前候选帧，回到搜索帧头状态；不执行命令、不返回响应。
4. 搜索连续 `A5 A5 5A` 时，第二个 `A5` 可以作为新帧起点。失败候选帧不要求回溯重扫，依靠手机超时重传恢复。
5. 在完整帧 CRC 正确之后才执行命令。接收缓存至少容纳一个最大帧；读取 BRAM 或处理播放时不能停止服务 UART。
6. 对 CRC 正确但 VERSION 非 1 的请求，按 v1 响应格式返回 `02`，不改变会话、曲谱或序号状态。来自手机的响应类 CMD（最高位为 1）直接丢弃。

这些超时针对 v1 规定的两档 UART。若后续使用更低波特率或改变最大载荷，必须重新评估超时。

## 4. 会话、序号和重传

采用停等：手机同一时间只能有一个未确认请求，收到匹配响应后才能发送下一个请求。

- 首次连接、重新连接、序号用尽、遇到序号冲突或连续重试失败后，手机先发 `HELLO`，SEQ 固定为 0、载荷为空。
- `HELLO` 终止未完成上传并释放上传状态，但不停止现有有效曲谱的播放，也不删除有效曲谱。已被 BEGIN 作废的旧曲不会恢复。
- HELLO 成功后，普通请求 SEQ 从 1 开始，逐次加 1，最多到 65535，不直接回绕。手机开始 HELLO 前必须取消旧会话的发送任务并清空本地旧解析缓存。
- FPGA 记录 `expected_seq`、最近一次普通请求的完整内容及完整响应。请求必须为 v1、CRC 正确，才进入序号处理。
- SEQ 等于 expected_seq：执行请求，包括参数错误或状态错误的请求；缓存其响应，然后 expected_seq 加 1。可用 17 位内部计数表示 65536。
- SEQ 等于最近一次已处理序号，且请求内容逐字节一致：仅重发缓存响应，不再次写 RAM、不再次启动播放、不再次更新曲谱 CRC。
- 同一序号而内容不同，或其他不符合 expected_seq 的序号：返回 `0B`，不执行、不推进序号、不覆盖缓存。手机重新 HELLO。
- CRC 错误或不完整帧没有响应。手机等不到响应时，重发完全相同的帧和 SEQ，不能换序号。
- 响应等待超时为 2000ms，自请求最后一个字节发送完成后起算；最多重传 3 次，即共发送 4 次。仍失败则结束本次操作，提示重连后重新上传。
- 正确响应必须同时满足 CRC 正确、VERSION=1、CMD 匹配且 SEQ 匹配；其他响应不能完成当前请求。
- 对已经收到的业务错误响应，手机不能盲目重发旧帧尝试修正；修改参数使用新 SEQ，必要时 ABORT 后重新 BEGIN。
- HELLO 重试仍用 SEQ=0。重复 HELLO 的重置行为可重复执行；手机在 HELLO 成功前不得开始上传。

响应均以 1 字节 STATUS 开始。除下文明确列出的成功响应外，错误响应的 LEN 固定为 1，仅包含 STATUS。正常处理应在 500ms 内返回响应，包括 COMMIT 的整曲检查。

## 5. 曲谱记录

每条音符固定为 8 字节，不带填充，所有记录按 start_ms 非递减排序。相同开始时间的记录保持手机发送顺序，以记录索引作为稳定次序。

| 偏移 | 字段 | 类型 | 约束 |
|---:|---|---|---|
| 0 | start_ms | uint32 | 从歌曲开始计时，单位 ms |
| 4 | note | uint8 | MIDI 音符号，处于 FPGA 报告的 note_min～note_max |
| 5 | velocity | uint8 | 1～127；0 为非法，休止通过时间空隙表达 |
| 6 | duration_ms | uint16 | 1～65535ms |

- `end_ms = start_ms + duration_ms`，使用扩展位运算检查溢出；必须不大于 FPGA 报告的 max_song_ms。
- 歌曲长度为所有 end_ms 的最大值；无需额外结束标记。
- 有效音符数量为 1～max_notes。不得静默截断、丢掉超音域音符或超出声部数的音符。
- 每条记录占用一个逻辑声部，活跃区间为 `[start_ms, end_ms)`；同一时刻先释放结束音符，再分配开始音符。相同音高重叠也按独立记录计数。
- 任何时刻活跃记录数不得大于 max_voices。手机预检查，FPGA 在 COMMIT 再检查；MAX_VOICES=1 时和弦与其他重叠音符均不合法。
- 声部在逻辑结束时可以被下一音符复用；ADSR 释放尾音的音质属于发声引擎实现，不延长协议中的逻辑声部占用时间。
- 手机将 MIDI 速度图换算成毫秒后发送；v1 不发送 BPM 或 MIDI tick。舍入统一使用最近整数毫秒，恰好 0.5ms 时向上；每个音符先独立计算开始和结束绝对时间，再计算持续时间。若舍入后持续时间为 0，手机须提示修正，不能静默通过。

### 5.1 整曲 CRC32

- CRC-32/ISO-HDLC：宽度 32，poly=`0x04C11DB7`（右移实现反射多项式为 `0xEDB88320`），init=`0xFFFFFFFF`，RefIn=true，RefOut=true，XorOut=`0xFFFFFFFF`。
- 覆盖按记录顺序拼接的全部 `note_count × 8` 个原始字节，不含 DATA 的索引字段、通信帧头或 CRC16。
- 标准校验：ASCII `123456789` 得到 `0xCBF43926`。
- CRC32 以 uint32 小端序置于 BEGIN 中。重复 DATA 不得重复计入累计 CRC。

## 6. 命令清单

| 请求 CMD | 名称 | 请求载荷 | 成功响应载荷 |
|---|---|---|---|
| `01` | HELLO | 空，SEQ=0 | 能力信息，见 6.1 |
| `10` | BEGIN | note_count:u16 + score_crc32:u32，共6字节 | status:u8=0 + next_index:u16=0 |
| `11` | DATA | first_index:u16 + 连续音符记录 | status:u8=0 + next_index:u16 |
| `12` | COMMIT | 空 | status:u8=0 + song_duration_ms:u32 |
| `13` | ABORT | 空 | status:u8=0 |
| `20` | PLAY | 空 | status:u8=0 |
| `21` | PAUSE | 空 | status:u8=0 |
| `22` | RESUME | 空 | status:u8=0 |
| `23` | STOP | 空 | status:u8=0 |
| `30` | GET_STATUS | 空 | 状态信息，见 6.2 |

例如 DATA 的响应 CMD 为 `91`。空载荷命令收到非零 LEN，返回 `03`。

### 6.1 HELLO 能力响应，固定 20 字节

| 偏移 | 字段 | 类型 | 含义 |
|---:|---|---|---|
| 0 | status | u8 | 成功为 0 |
| 1 | min_version | u8 | 1 |
| 2 | max_version | u8 | 1 |
| 3 | max_payload | u16 | 256 |
| 5 | max_notes | u16 | 实际可用曲谱记录数，建议 1024 |
| 7 | max_voices | u8 | 实际支持同时活跃的记录数，至少1 |
| 8 | note_min | u8 | 发声引擎实际支持的最低 MIDI 音符号 |
| 9 | note_max | u8 | 发声引擎实际支持的最高 MIDI 音符号 |
| 10 | features | u16 | 见下方 |
| 12 | uart_baud | u32 | FPGA 当前 UART 配置，不是自动测量值 |
| 16 | max_song_ms | u32 | 建议 3,600,000，即1小时 |

features：bit0=支持 PAUSE/RESUME，bit1=曲谱掉电保留，bit2=支持多声部；其余保留为0。v1 必须支持暂停，因此 bit0=1；RAM 版本 bit1=0；bit2 当且仅当 max_voices>1 时为1。单声部 RAM 版本为 `0x0001`，多声部 RAM 版本为 `0x0005`。

容量、音域、声部数取自实际已实现的 FPGA 参数，不能把规划值当作已具备的能力。手机不得通过 uart_baud 字段自动修改模块的 AT 参数。

### 6.2 GET_STATUS 成功响应，固定 13 字节

| 偏移 | 字段 | 类型 | 含义 |
|---:|---|---|---|
| 0 | status | u8 | 本请求成功为0 |
| 1 | song_valid | u8 | 0无有效曲谱，1有有效曲谱 |
| 2 | upload_active | u8 | 0无上传，1上传中 |
| 3 | play_state | u8 | 0停止，1播放，2暂停 |
| 4 | received_notes | u16 | 已成功写入的音符数量；成功 COMMIT 后保持完整数量 |
| 6 | total_notes | u16 | 当前有效曲谱或当前上传的预期数量；无两者时为0 |
| 8 | position_ms | u32 | 播放进度；暂停冻结；STOP 归零；自然结束保留歌曲长度 |
| 12 | last_error | u8 | 最近一次业务错误；上电或 HELLO 清零，成功业务请求不自动清零 |

序号冲突也记录到 last_error；无法确认完整头和 CRC 的坏帧只丢弃，不更新此字段。手机最多每500ms轮询一次，且必须等当前命令完成后再轮询。轮询也消耗普通 SEQ。

## 7. 状态与命令语义

上电默认 `song_valid=0, upload_active=0, play_state=0`；必须先 HELLO。所有状态变化均发生在请求完整校验通过后。

### 7.1 上传

1. BEGIN 仅允许 play_state=0 且 upload_active=0。手机若正在播放或暂停，先 STOP。
2. BEGIN 先检查 note_count 在容量内。参数不合法时保留原有效曲谱；成功后立即令 song_valid=0，upload_active=1，received_notes=0，position_ms=0，初始化整曲 CRC。上传期间发声输出静音。
3. DATA 的 `LEN=2+8×k`，k 为1～31。推荐每包16条，即128字节音符数据、130字节载荷。最后一包可以不足16条。
4. first_index 必须等于 received_notes，且 first_index+k≤total_notes。FPGA 缓存并检查整包的结构、音域、力度、时长、时间范围和与已有记录的非递减顺序，全部通过后才写入并推进计数；非法包不产生部分写入。第一版可在 COMMIT 统一检查声部重叠。
5. DATA 成功响应 next_index=first_index+k。手机核对该值，不一致则 ABORT 并重传整曲。进度条使用确认过的 next_index/total_notes。
6. COMMIT 仅在上传中且 received_notes=total_notes 时执行。CRC32 不符返回 `09`；时间/音符/排序/声部约束不符返回 `0A`。这两类最终校验失败都会结束上传、清零曲谱计数并保持 song_valid=0，手机重新 BEGIN。
7. COMMIT 因“尚未收满”返回 `05`，保留上传状态，允许继续 DATA。
8. COMMIT 成功令 song_valid=1，upload_active=0，play_state=0，position_ms=0，保留曲谱计数，并返回歌曲长度。只有此时手机才能显示“下载成功”。
9. ABORT 在上传中使上传结束、曲谱无效、计数与进度归零；没有上传时作为成功的空操作，不删除已有有效曲谱，不停止正在播放的曲谱。
10. 上传中连续30秒没有成功处理 BEGIN 或新 DATA，则自动执行与上传中 ABORT 相同的清理，last_error=0C；GET_STATUS 和重复缓存响应不续期。COMMIT 检查期间不触发此超时。
11. 上传中仅允许 DATA、COMMIT、ABORT、STOP、GET_STATUS、HELLO；新 BEGIN、PLAY、PAUSE、RESUME 返回 `05`。

### 7.2 播放与手动琴键

- PLAY：要求 song_valid=1 且没有上传；从0ms开始播放。新的 PLAY 请求即使当前正在播放或暂停也重新从头开始；同 SEQ 重传只返回缓存响应，不重启。
- PAUSE：要求有效曲谱且正在播放或暂停；冻结 position_ms，保存逻辑活跃记录及其剩余时间，静音；已经暂停时返回成功。
- RESUME：要求有效曲谱且正在播放或暂停；暂停时恢复音乐时间，重新触发原活跃记录并按剩余时间结束。包络从头触发，不承诺保留波形相位或包络内部进度；已经播放时返回成功。
- STOP：始终可执行，清除自动播放声部、令 play_state=0、position_ms=0；不删除有效曲谱，不终止正在上传的事务。
- 自然播放结束：最后一条记录结束时令 play_state=0，position_ms 保持歌曲长度；再次 PLAY 从头开始。
- 上传、自动播放、暂停时暂时屏蔽手动琴键；有效曲谱待机或无曲谱待机时允许手动演奏。上传中 STOP 后仍保持上传静音。
- 模式切换时清除前一模式的活跃音符与触发信号。恢复手动模式后，对切换时已经按住的键，应等待释放后重新按下再触发，防止切换造成意外起音。
- 调度器按每个逻辑声部处理结束事件；不能仅按音高发送全局 note_off，以免提前结束同音高的其他记录。

## 8. STATUS 错误码

| 值 | 名称 | 含义/手机处理 |
|---|---|---|
| `00` | OK | 成功 |
| `01` | UNKNOWN_CMD | 不支持的命令；检查实现版本 |
| `02` | BAD_VERSION | 不支持协议版本；停止业务操作 |
| `03` | BAD_LENGTH | 载荷长度或记录对齐错误；修正打包 |
| `05` | BAD_STATE | 未 HELLO、状态不允许或 COMMIT 时尚未收满 |
| `06` | BAD_PARAMETER | BEGIN 数量为0、DATA 音域/力度/时长/时间/排序等参数错误 |
| `07` | BAD_OFFSET | DATA 索引不是当前 next_index；ABORT 后重新上传 |
| `08` | NO_SPACE | BEGIN 超过容量，或 DATA 超过声明的 total_notes |
| `09` | SCORE_CRC_MISMATCH | 整曲 CRC32 错误；当前上传已作废 |
| `0A` | INVALID_SCORE | COMMIT 整曲约束检查不通过，例如声部重叠超限；当前上传已作废 |
| `0B` | SEQ_CONFLICT | 序号不同步或重复序号内容不一致；重新 HELLO |
| `0C` | UPLOAD_TIMEOUT | 上传事务超时，主要通过 GET_STATUS 的 last_error 报告 |
| `0D` | INTERNAL_ERROR | 内部执行失败；清理当前上传或停止播放后返回，重新 HELLO |
| `0E` | NO_VALID_SCORE | PLAY/PAUSE/RESUME 没有有效曲谱 |

`04` 保留，不用于坏帧响应。长度/状态错误的检查顺序：先检查命令是否存在及载荷结构，再检查会话与状态，再检查业务参数。普通序号不匹配优先返回 `0B`。错误响应不得改变既有业务状态，本文明确规定的 COMMIT 最终校验失败和内部错误除外。

## 9. 完整交互示例

```text
手机                                    FPGA
HELLO(seq=0) -------------------------->
             <-------------------------- 能力信息
STOP(seq=1，如有必要) ------------------>
             <-------------------------- OK
BEGIN(数量、整曲CRC32) -----------------> 旧曲失效，准备RAM
             <-------------------------- OK,next_index=0
DATA(index=0,16条) --------------------->
             <-------------------------- OK,next_index=16
DATA(index=16,16条) -------------------->
             <--- 响应丢失 ---           已经写入
相同DATA、相同SEQ重传 ----------------->
             <-------------------------- 缓存响应，不重复写入
... 所有DATA确认 ...
COMMIT --------------------------------> 校验整曲
             <-------------------------- OK,歌曲长度
手机显示“下载成功”
PLAY ---------------------------------->
             <-------------------------- OK；由FPGA本地计时播放
```

手机蓝牙断开时，未完成上传最多30秒自动清理，或下次 HELLO 立即清理。已经完整下载的曲谱可继续本地播放；模块 STATE 引脚仅作额外状态提示，不作为协议正确性的必要条件。
