# 多声部、琴端选曲与Flash曲库开发计划

日期：2026-10-24，后续状态更新2026-10-25。本文保留功能规划依据；当前A～G已本地接入实现，H的软件/HDL联调见[扩展接口与阶段验收](扩展接口与阶段验收.md)，实物Flash、手机、新STA和长期验收尚待用户执行。下文“建议/待确认”描述规划提出时的背景，不能当作已实测能力。

## 1. 目标与已确认事项

本计划取代此前以App状态同步、美化为下一阶段重点的安排。优先实现三个独立功能：

1. 蓝牙下载曲谱支持多声部，复用已有音色和回声/房间混响/颤音。
2. FPGA本地可以查看曲谱、选择、播放、暂停、继续和停止，不依赖手机持续在线。
3. 下载曲谱写入Flash，FPGA本地可以管理多首曲谱，断电后目录与已提交曲谱仍存在。

设置页仅增加一个可见入口 `more`。所有新功能在该入口内用简洁字符显示和操作；首版不进行配色、图标、动画或复杂排版优化。独立模块可共用音源、效果器和播放器内核，不为“独立”复制多套公共计算通路。模块的命令、状态、错误和测试独立；UI仅作适配，不成为业务逻辑所在地。

用户已实测确认App连接、通信、MIDI文件下载播放、暂停及停止正常，这些作为回归基线；不能据此宣称多声部、Flash、继续/自然结束或全部时序已经验收。继续保留App“连接模块”和“验证FPGA”两个独立入口。

用户确认使用板载第二颗Flash，允许调整对应LED用途。2026-10-26纠正：U7 MOSI实际是R21，与N21 LED没有共用关系。助手仍只开发RTL/约束/脚本/文档和运行软件/HDL验证；综合、P&R、STA、下载与实物Flash读写验收由用户执行。

## 2. 参数建议与需要区分的概念

| 项目 | 计划建议 | 状态与理由 |
|---|---|---|
| 自动播放复音 | 首阶段目标16声部，参数化 | 用户询问一般曲谱需求后提出的建议，尚不是已实现能力；8适合较简单旋律伴奏，16减少普通多轨筛选限制，但不保证所有MIDI都能播放 |
| 音色 | 首版使用琴端当前选定音色 | 多声部不等于多音色；暂不按MIDI轨道/Program Change自动分配七种音色 |
| 效果器 | 复用现有混音后的全局三效果器与参数 | 不增加每声部独立效果器，不复制延迟/混响RAM |
| 单曲容量 | 建议目标4096条记录，参数化 | 32KiB事件RAM；从现有1024条增加需独立验证资源和协议能力报告，不静默截谱 |
| Flash曲目数 | 建议首版32首，固定槽位 | 目录小、无需复杂文件系统；条数和最终分区待型号/可用区域识别后冻结 |
| 上电行为 | 静音待机，允许手动演奏；以后独立扫描Flash目录 | 用户已要求取消上电小星星；USR复位也不重播。曲谱仅在用户明确播放后启动 |

复音数指转换后半开区间 `[start,end)` 的最大同时活跃记录数，不是轨道数量。同音高重叠也需要不同声部；释放尾音可能继续占用物理音源资源。例：单旋律1声部，旋律加三音和弦至少4声部；实际钢琴、多轨或长音叠加可能更多。App必须统计每首曲谱的真实需求，以HELLO报告能力校验，超限明确拒绝，不自动删音。

当前仍忽略踏板/弯音等MIDI控制，保留简化演奏提示；本次不顺带加入踏板、自动主旋律提取、实时蓝牙演奏或远程编辑音符。若用户需要分轨多音色，应在协议冻结前补充，它会影响记录或元数据设计。

## 3. 模块边界与数据流

| 模块/职责 | 输入 | 输出与边界 |
|---|---|---|
| 蓝牙协议适配 | v1帧、扩展命令 | 上传事务与控制请求；不直接操作音源寄存器或绘制UI |
| 曲谱校验/活动RAM存储 | 64位音符记录、容量、CRC | 完整有效曲谱；对蓝牙和Flash加载使用同一格式校验 |
| 通用曲谱调度内核 | 活动RAM、逻辑时间与控制命令 | 带独立身份/音高/力度的On/Off；原调度器原位抽象复用，不复制一套Flash专用播放器 |
| 多声部音源适配 | 原子音符事件及确认 | 映射到已有32物理声部；与键盘身份隔离，维护每个自动声部的力度/实际音高 |
| 本地曲谱控制 | 选曲/播放/暂停/继续/停止请求 | 调用目录、加载与播放器接口，具有独立状态机，不依赖手机连接 |
| Flash底层 | 有界地址读/页编程/块擦除请求 | JEDEC识别、忙状态、完成/错误；不解释曲名和音符 |
| Flash曲库管理 | 保存、列表、加载、删除 | 目录、曲目元数据、事务状态；实现掉电一致性，与物理SPI细节隔离 |
| 命令/资源仲裁 | 手机与本地控制请求 | 单一播放所有者、RAM和Flash占用规则；冲突明确BUSY，不让两个入口同时控制同一事务 |
| more UI适配 | 按钮/触摸与各模块状态 | 只映射命令及文字，不把擦写、调度或协议状态机写进渲染器 |

数据流：App MIDI解析 → 验证并下载到活动RAM → 完整校验 → 曲库保存任务 → Flash持久目录。

本地播放：Flash目录选择曲目 → 载入活动RAM并核验CRC/复音约束 → 通用播放器 → 多声部音源 → 现有效果器 → 音量/I²S。

活动RAM一次仅装一首。曲库容量与单曲RAM容量分别报告；不把Flash空闲大误认为可以上传任意长曲谱。首版不使用实时Flash流播、DDR或全功能FAT文件系统，以降低调度耦合与资源开销。

## 4. 多声部与效果器接入

当前调度器已有VOICES参数，但顶层MAX_VOICES=1；音源适配器强制note_id=0，每个新On进入CLEAR；力度/实际音高也仅为ID0保存。修改目标包括：

- 将每个逻辑自动声部分配独立身份，明确与手动键盘及原曲谱源的命名空间/所有权。Note Off按声部身份处理，不能仅按音高关闭。
- 保存各自动声部自己的力度和音高，保持音符高亮及音色载荷正确。释放声部复用、同音重叠、尾音与抢占均要有明确语义。
- 普通On/Off不全局清空音源或效果RAM；切换来源、暂停、STOP等控制采用专门的清场流程及真实音频确认。
- 保留现有三效果器的全局选择和参数接口，蓝牙/Flash曲谱混音自然经过同一效果器。首版音色与效果由琴端既有设置选择，不为快速完成先添加未经协商的App效果命令。
- 在多声部设置下重测音量、削波和峰值余量；不能直接取消现有缩放，也不能把“能同时响”当作音质合格。
- 在1ms内处理最大合法同毫秒事件簇，包括最多16 Off + 16 On、暂停恢复、CDC往返与音源背压。不能把32逻辑事件组合展开成巨大比较/多路选择网络。

音频不平滑的既有问题继续按音质规划分开定位；本阶段必须去掉会破坏多声部的逐音全局flush，但不捆绑FIR、完整音色重做或界面美化。

## 5. Flash依据与接入

官方规格和本地4071/4072原理图第7页标注两颗128Mbit Flash，即每颗标称16MiB；实际型号和可用分区不能由容量标注推定。候选U7连接由已视读的4072原理图给出：CS=L25、CLK=P20、IO0=R21、IO1=T22、IO2=R22、IO3=R20。首版优先单线SPI，只使用必要信号；其余IO保持芯片要求的非激活状态。最终约束还需与实际核心板版本及器件要求核对。

2026-10-26更正：原计划误把N21 LED当作U7 MOSI，真实U7 IO0为R21，N21是独立USR_LED1。现有五灯编号保持，N21闲置；不需要为Flash驱动该LED。

先只读JEDEC ID、状态与必要的SFDP/已知标识，核对型号、容量、IO电压、页大小、擦除粒度、保护位与现有内容。未识别型号或未划定允许区域时不擦写。不使用整片擦除，不接管U4配置Flash，不覆盖FPGA启动镜像或未知已有数据。确定可用区域后才冻结曲库物理起止地址。

Flash驱动在参考时钟域用CE推进，SPI时钟为输出信号，不作为内部派生时钟。所有编程/擦除均有忙状态轮询、超时、错误反馈和地址边界检查；读写页界限和NOR的1→0编程规则由型号对应驱动负责。

## 6. 曲库布局与掉电一致性

首版采用固定最大目录、固定上限槽位和独立备用空间：

- 元数据包含格式版本、曲目ID、有限长度名称/显示编号、记录数、时长、最大复音、音域、数据CRC、代数及提交标记。
- FPGA优先显示S001等编号和简短ASCII名称。中文名可由App保留显示，琴端先回退编号，不添加大中文字库或输入法。
- 新数据先写备用槽位，读回核验成功后再提交新目录；双目录/日志记录采用CRC和代数选择最近完整版本。NOR提交标记必须符合实际编程规则。
- 替换和删除也使用目录事务；擦写或掉电失败后保留旧完整目录，或识别未完成新曲，不出现“列表有效却播放半首”的情况。
- 目录更新成功后再回收旧数据。保留备用槽位，容量满时仍须有明确的原子替换策略，否则拒绝操作。
- 首版提供保存、列表、查看信息、加载、删除及容量/错误状态；删除需字符确认。复杂排序、文件夹、搜索、琴端文字编辑、全盘格式化不列首版。
- 上电目录恢复为独立任务，Flash损坏或缺失不能无限阻塞手动演奏；进入只读/错误状态并允许其他功能工作。

建议32首×4096条，每首原始记录32KiB，32首约1MiB；实际还要加页/擦除对齐、元数据、双目录与备用空间。最终数量以保护分区、综合资源和实测芯片为准，不把名义16MiB全部当作已可用曲库。

首版停止播放后才允许加载、上传、擦写和删除；运行期间允许查看已缓存的目录/状态。手机和琴端若同时请求写操作，单一仲裁器只接受一个，其他返回BUSY，避免边播边擦写的复杂性。后续可独立扩展，不影响接口分层。

## 7. 协议与App协同

多声部仍使用8字节音符记录和现有基本命令；HELLO按真实MAX_VOICES报告，旧单旋律文件继续可用。单曲容量增加时同步调整校验、索引位宽、RAM、App预检查与测试，不只改显示数字。

Flash目录、曲名、选择与保存不在现有v1命令中，需要先制定扩展协议。建议保留现有帧格式、HELLO长度、保留位含义及COMMIT行为，新增可探测的扩展能力、目录列表、保存、加载、删除和任务状态命令；不直接复用既有错误码/功能位造成旧App误判。旧0.2仍可走既有RAM下载路径，新App探测曲库扩展后启用自动持久保存流程。

正常新App下载流程：BEGIN/DATA/COMMIT确认RAM有效 → 发起保存任务 → 返回任务ID → 查询保存状态 → Flash核验并提交目录 → 显示“已保存到琴”。Flash擦除可能长于普通应答预算，因此任务启动快速返回，异步查询进度，不能简单把旧COMMIT应答延迟到整个擦写结束。

“数据已接收/已校验”“正在保存Flash”“已持久保存”必须区分。保存失败时不宣称掉电保留，已保存旧曲不能被失败事务破坏。任务命令重传必须幂等，不能同一请求重复分配槽位或再次擦除；断线/重连后也能查明任务最终状态或明确结果未知。

App仅补充本阶段必需功能：多声部能力预检查、曲目编号/短名、自动持久保存及状态；保持模块连接/FPGA验证两步入口。App曲库UI美化、远程音色/效果控制及复杂歌曲编辑后置。

## 8. more入口与操作

仅在原设置页增加 `more`，不在演奏页和原设置页散落新按钮。注意现有 `UI_MORE` 已是效果强度增加动作，新入口必须另取动作标识，例如 `UI_OPEN_MORE`，不能复用导致误触。

more内先用固定字符行和少量分页：

```text
MORE
BT     POLY 16   READY
SONGS  S001     PLAY / PAUSE / STOP
FLASH  SAVE / DELETE / INFO
BACK
```

界面示意仅表示并列入口；BT、SONGS、FLASH各自进入独立控制适配，不共享一个巨型业务状态机。页内固定行显示编号、条数、时长、BUSY、ERROR即可。复用已有字库和选中行标识，限制每页目录条数，按页取数据，避免把全曲名/全目录跨时钟传给渲染器。

触摸和矩阵输入统一映射到同一动作接口，保留退出、上一/下一、确认/取消；more期间沿用菜单禁止误发音、退出须松键的规则。仅“more”作为新一级入口，UI美化作为最后阶段验收之后的独立任务。

## 9. 分阶段开发与验收

| 阶段 | 工作 | 独立验收 |
|---|---|---|
| A 基线与接口冻结 | 记录当前已测版本，审计已有时序问题；冻结声部身份、RAM端口、存储任务与本地控制接口 | 接口文档、资源/周期预算和测试向量；不依赖UI就能驱动各模块 |
| B 多声部/效果器 | 目标16逻辑声部、逐声部力度与音高、移除逐音flush、复用三效果器 | 和弦/同音重叠/密集事件、暂停恢复和停止；App真实下载16声部曲谱并调用琴端效果 |
| C 本地控制 | 用RAM和仿真目录源完成列表/选择/加载/播放控制；抽象通用调度与来源仲裁 | 手机断开后本地命令可独立工作；冲突BUSY、退出与接管无挂音 |
| D Flash底层 | 确认实际板版/芯片ID、R21映射、地址边界、读写/忙超时模型 | 用户先实测只读，再在明确的测试区域写入/读回；配置区不变 |
| E 持久曲库 | 固定槽位、元数据、双目录/日志、加载删除及恢复 | 逐页/目录提交中断与掉电模拟；多首歌曲重启后完整可查可播 |
| F 协议/App | 曲库扩展、保存任务、持久状态与多声部预检查 | 旧RAM路径兼容、新App保存成功含义正确，重传/断线不重复擦写 |
| G 最小more集成 | 设置页一个新入口；字符列表与各独立动作适配 | 完成琴端选曲、播放、删除、容量/错误查询；触摸/矩阵无误发音 |
| H 联调与交付 | 对照源码/位流/报告，回归原UI/触摸/七音色/手动演奏 | 新STA满足全部时钟与接口要求；用户实板多首/多声部/掉电恢复与长稳记录 |

底层测试与各模块开发独立推进，UI不是前置条件。最终挂载more之前用仿真命令验证功能；不以虚构目录或RAM模拟持久化宣布Flash阶段完成。

## 10. 时序与资源约束

已读取17:50:08报告：音频要求61.44MHz、报告Fmax55.847MHz，全工程Setup违例端点1276（音频内部257）；像素要求35MHz、报告Fmax33.134MHz。此报告不证明实际噪声原因，但新功能不能建立在“已时序通过”的假设上。

复用同步RAM、顺序校验与调度，保持短载荷CDC/原子快照；不新增2048位帧总线、并行大表比较、长目录组合MUX或组合展开16声部。Flash读写不能阻塞音频采样，UI不能驱动业务长组合路径。不通过全局降频或宽泛false path掩盖问题。软件/HDL验证由助手执行，用户按阶段进行综合/P&R/STA及实物测试。

## 11. 待补充确认与默认建议

- 板载第二颗Flash：用户已确认；实际MOSI为R21，参见上方更正。
- 复音目标：推荐16；一般曲谱没有统一固定数量，需按文件实际最大重叠校验。16是当前建议，不是已实现或对所有曲谱的保证。
- 单曲/曲库容量：建议4096条、32首；若更看重极低资源，可保留1024条，代价是更容易超限。暂不增加分页流播复杂度。
- 音色/效果：默认统一采用琴端选择；是否需要同曲分轨多音色或App远程效果控制，需作为额外范围明确，不能由“多声部”自动推导。
- 核心板4071/4072实际版本、第二颗芯片JEDEC型号、允许使用的已有区域：由只读核对和用户实物测试补齐，不要求先猜品牌或擦除全片。
