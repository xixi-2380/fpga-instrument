# App 首版需求与重构顺序

日期：2026-10-24。状态：需求分析；本轮未修改 Android/FPGA 功能代码、未构建 APK、未进行手机连接测试。

后续执行补充：用户已确认P0/P1合并为同一轮交付，但App保留两个独立验证入口。2026-10-24已实现0.2开发版，软件验证与安装说明见 `android/README.md`、`reports/android_connection/validation.json`；仍未手机/无线验收。下文保留需求分析时的范围，P0/P1验收改为同一APK内分步执行。

## 1. 当前问题与目标

用户明确反馈：现有 App 近乎不可用；EC05 已配对，其他蓝牙串口软件能正常连接，但本 App 下手机没有与模块建立连接，模块仍处于等待连接状态。因此当前 P0 是 App 的真实蓝牙连接失败，优先检查 RFCOMM 建连；不能把它解释成已连接但 HELLO 失败，也不能继续默认模块不可用或要求重新核对既有接线。

工作对象为 `E:\gowin\fpga-instrument-bt-score\android`，沿用该工作树已实现的 v1 FPGA 协议。首版目标是让用户在手机独立完成：连接琴 → 导入 MIDI → 选择声部/移调 → 预检查 → 下载到琴 → 播放/暂停/继续/停止 → 异常恢复。重构先恢复实际可用性，随后完善状态管理和界面，不以核心测试通过代替手机可用。

保留原规划、协议及黄金数据原文，不在本轮改变 FPGA RTL、接线、音色或时序；另一个已恢复的 `E:\gowin\fpga-instrument` 不受本轮 App 重构影响。

## 2. P0：先修真实蓝牙连接

### 已确认的代码事实

- `MainActivity.connect()` 目前仅使用 `createRfcommSocketToServiceRecord`，固定标准 SPP UUID `00001101-0000-1000-8000-00805F9B34FB`，没有 insecure RFCOMM 兼容路径。
- Socket 建连与 HELLO 合并在一个任务内；没有阶段独立的界面反馈和错误分类。即使后续修好建连，也需明确展示蓝牙连接与业务握手两种状态。
- 连接超时15秒，后台执行；此前不能据此认定没有连接竞态或资源清理问题。`pendingSocket`、当前客户端、超时任务与界面由 Activity 分别管理，需要审计取消/重试时的归属和过期回调。
- 没有发现建连前取消发现过程的调用；若要引入 `cancelDiscovery`，必须一并核对 Android 版本对应权限，不能无条件调用而引发权限异常。
- 目前没有手机异常堆栈或蓝牙日志，因此还不能把 secure/insecure 模式、发现过程、连接占用、权限或竞态中的某一项写成已证实根因。

### 必须完成的行为

1. 选择已配对设备后显示设备标识和“正在建立蓝牙连接”；Socket 成功后立即显示“模块已连接，正在与FPGA握手”，再发 HELLO。
2. 保持界面可响应，连接过程始终可取消。取消、失败、超时或切换设备必须关闭该次 Socket、清理看门狗，旧任务不得覆盖新连接状态。
3. 标准 SPP 建连兼容性优先审查 secure/insecure RFCOMM 的差异，必要时采用明确、有限的兼容尝试。每次尝试使用独立 Socket，失败后彻底关闭；不盲猜 UUID、不依赖反射强制通道1、不无限重连。
4. 版本化处理权限拒绝、蓝牙关闭、设备不可达和服务连接失败；错误界面给出当前失败阶段与可执行下一步。其他软件占用连接只能作为测试条件之一，不能当成未经验证的原因。
5. 开发诊断记录连接方式、阶段耗时、异常类型/堆栈、关闭原因与会话编号；普通界面显示可理解的错误，不要求用户读十六进制判断是否连上。
6. 将“只建立连接”和“协议握手”分层测试。只连接测试不发送任意文本或 AT 命令；连接成功不能伪造为琴端协议已就绪。

P0 验收：同一手机、同一模块，在其他串口软件释放连接的对照条件下，本 App 真实建立并保持连接，模块状态与手机端一致；连续连接/断开至少10次，包含取消和超时恢复，无需反复重启 App 才能恢复。若仍失败，必须有明确的建连阶段异常，不能只显示“连接失败”。HELLO 此时作为单独的下一步验收。

## 3. P1：握手与设备状态

- Socket 建立后发送 v1 HELLO；收到版本、CMD、SEQ、CRC、长度与能力字段均正确的应答，才进入“电子琴就绪”。黄金请求为 `A5 5A 01 01 00 00 00 00 E1 E1`。
- 区分“连接失败”“连接已断开”“模块已连接但FPGA未应答”“收到损坏/不兼容响应”，分别记录 TX/RX 字节计数与协议诊断，不吞掉错误后统一报超时。
- 保持停等、最多4次同帧同序号发送、2秒应答超时及序号规则。重连/新会话清空旧解析数据；不靠修改序号、CRC或增加未知命令绕过故障。
- 握手后读取设备状态。HELLO 不停止有效曲谱；重连后根据琴端状态恢复界面，不自行宣称设备已停止或曲谱已清空。
- 能力来自 HELLO。当前 FPGA 配置为1024条记录、1自动调度声部、MIDI48～83、RAM掉电丢失；不得把手动32声部或模拟器4声部当成自动播放能力。
- 读取断开/EOF必须主动通知会话管理，关闭设备操作入口；旧进度、歌曲身份和播放状态标为未知或待刷新。

## 4. 首版完整功能

| 功能 | 必须支持 | 首版边界 |
|---|---|---|
| 设备连接 | 已配对设备列表、真实连接/断开/重试、阶段状态、HELLO与能力显示 | 先完成已配对模块连接，不以新增扫描代替修复 |
| MIDI导入 | 系统文件选择器；Format0/1、PPQN、全曲速度图、Note On/Off与velocity0、running status | 不解析图片、PDF、MP3；Format2/SMPTE明确拒绝 |
| 声部与预览 | 全部或单一轨道、全部或单一通道、半音移调、音符数/音域/时长/最大重叠数 | 不承诺自动提取主旋律；单轨也可能含和弦 |
| 设备预检查 | 依据HELLO校验音域、容量、时长及同时音符数，提示具体修正办法 | 不能静默丢音、截谱或自动改时值来满足单声部 |
| 下载 | 替换确认、STOP→BEGIN→DATA→COMMIT、按ACK更新进度、取消ABORT | RAM单曲；数据100%后仍须等待COMMIT成功 |
| 播放 | 播放、暂停、继续、停止；琴端状态与时间显示；自然结束后更新界面 | 不提供跳转、实时调速、远程琴键或手机合成试听 |
| 异常恢复 | 断线、权限变化、超时、FPGA复位、取消、序号冲突的明确恢复路径 | 重连HELLO后完整重传，不承诺断点续传 |
| 示例/演示 | 三音符1900ms示例；离线演示明确标识且与真实会话隔离 | 演示不发声，不能证明真实连接或下载通过 |

MIDI保留原有严格配对、变速与毫秒舍入规则；踏板、弯音、音色/表情等被忽略时必须在上传前提示简化并确认。单音符时长1～65535ms，文件2MiB等解析资源上限沿用现有代码并清楚提示。设备容量/时长仍以HELLO为准。

手机只负责转谱与控琴；v1没有远程音量、音色、效果器命令，不能因琴端有设置页便在App加入无效开关。在线曲库、账户、多曲目设备存储、Flash、后台持续上传服务均不列为首版必需项。

## 5. 重构必须补齐的状态规则

采用独立的连接状态、手机曲谱草稿状态、琴端曲谱/播放状态和上传事务状态，不再用一个 `busy` 加“客户端非空”决定全部按钮。

- 未连接也可导入和预览；仅协议就绪后允许上传及琴端操作。播放/暂停/继续依据最后确认的设备状态启用。
- 更改轨道、通道、移调或源文件后，旧转换结果立即失效，重新生成与预检查后才允许上传。上传确认绑定一份不可变曲谱快照，不能显示新参数却发送旧音符。
- 连接、传输、查询保持单一命令队列；状态查询低频进行，上传期间不插队。自然结束要能被查询并更新，不能长期停留在“播放中”。
- 上传取消始终可达；“请求取消”“ABORT已确认”和“链路断开，琴端结果未知”分别显示。已完成COMMIT的竞态要按实际应答对账，不能一律声称撤销成功。
- 新BEGIN接受后旧曲失效，失败不恢复旧曲。重连发现有效曲谱时，v1不能读回曲名/整曲CRC，因此未知身份显示“设备有有效曲谱”，不能将本地同长度文件冒认为琴端歌曲。
- 常规旋转/界面重建不重复发送命令或泄漏连接；进程死亡/真正断开后按新会话恢复，不承诺后台持续传输。断开连接不等同于STOP，不自行改写琴端实际播放状态。

## 6. 哪些保留，哪些重构

保留 `Wire`、`MidiFile`、`Score`、`ProtocolClient` 中已有协议/解析规则与黄金测试；新增诊断和边界修复需保持已有向量兼容，不因UI改版全面重写正确的CRC/MIDI算法。

重点重构：蓝牙连接协调器（权限、Socket尝试、取消、超时和断开）、会话协调器（HELLO、命令与状态）、可测试的界面状态模型，以及Activity的展示/输入职责。阶段状态和错误通知先做，界面分区随后整理为“连接—曲谱—传送—播放”，开发日志放入可展开诊断区。

## 7. 验收与交付顺序

1. P0连接诊断和修复APK：验证真实建连、保持、取消、断开、重连。
2. P1 HELLO和状态：证明真实字节双向通路、能力校验和错误分层，不自动修改FPGA协议。
3. P2三音符闭环：上传黄金曲谱并核对1900ms，播放/暂停/继续/停止与自然结束，再验证取消、断线与重连。
4. P3 MIDI与状态体验：覆盖单旋律、多轨筛选、移调、超限、参数变更后禁止旧谱上传及界面重建。
5. P4交付：新APK、构建/签名与源码身份记录、手机/Android版本及真实连接结果；完整传谱播放至少20轮，记录失败。

现有36043项检查仅证明纯Java协议/MIDI核心的对应测试结果，不覆盖Android权限、Socket、Activity、安装、手机或无线连接。重构补充连接状态机的假传输测试与Android实际运行测试；纯Java模拟通过不能完成P0验收。旧APK沿用原产物，不能当作本轮重构版本。

## 8. 平台依据

- [Android经典蓝牙连接](https://developer.android.com/develop/connectivity/bluetooth/connect-bluetooth-devices)：RFCOMM建连与数据流、UUID匹配、后台执行阻塞的connect、发现过程对连接的影响。
- [Android BluetoothDevice](https://developer.android.com/reference/android/bluetooth/BluetoothDevice)：secure/insecure RFCOMM API及权限；它们是需要对照验证的连接选项，不是已确认的故障修复。
- [Android蓝牙权限](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)：按系统版本和实际操作声明、请求权限；既有配对不等于本App已获运行时权限。
